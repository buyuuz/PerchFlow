# PerchFlow Project Hub V1 — 开发与验证记录

## 决策与目标
在现有 PerchFlow「进程」「定时任务」之上增加 **项目管理层**，不再新建调度器。
项目把已有的 Python/命令行任务、工作目录、输入文件和输出文件建立关联；真正启动和定时执行仍由原来的 Scheduler 负责。

## 当前实现
- 新入口：`/projects`，管理项目名称、绝对工作目录、关联的既有任务，以及相对路径形式的输入/输出文件。
- 新 API（既有 Bearer Token 鉴权）：`GET/POST /api/projects`、`GET/PUT/DELETE /api/projects/:name`。
- 项目详情仅查询**配置过的**文件元数据（存在、大小、修改时间），不读取文件内容、不复制文件。
- 文件引用禁止绝对路径、盘符、`..`；查询时不跟随最终符号链接，检查 canonical path 仍在项目根目录下。
- 一个现有任务最多关联一个项目。被引用的任务不允许直接删除或改名，需先在项目中取消关联。
- 删除项目只删除 `perch.toml` 中的项目关系，不删除任务、日志、TXT/Excel/Python 文件。
- TOML 中 `[[project]]` 可选，原来的配置与任务无需迁移。
- 项目工作目录即使临时离线，也不阻止 PerchFlow 启动；文件状态显示不可用。

## 初次使用
1. 到 `/tasks` 添加 Python 任务，命令填写 Python 解释器绝对路径，参数填写 Python 脚本路径和启动参数，工作目录填写原项目目录。
2. **先保持任务 Disabled**，在 `/projects` 创建项目，填写名称、工作目录以及输入/输出文件的相对路径（每行一个）。
3. 在项目中勾选已有任务，保存后可查看任务入口、文件状态；执行、Cron、运行日志沿用原来的 `/tasks`。
4. 确认运行环境、安全性以及计划后，再考虑启用调度。不要直接导入真实账号或密钥到测试环境。

## 安全边界
- 开发代码只在 `feature/task-runtime-reliability`，不修改正式 `main` 和线上 PerchFlow。
- 所有自动测试都使用临时目录和完全虚构的输入/输出内容，不调用业务 Python、Firecrawl、Daily_Check、TikTok。
- API / 页面不得读取或显示账号密码或 Key 文件正文。原任务日志**可能包含脚本自身打印的敏感数据**，因此本阶段不自动展示文件内容，也不承诺对脚本 stdout 做可靠脱敏。
- 不自动清理临时文件、不批量移动/删除项目资源。

## 计划但尚未实现
- 单次执行前后文件快照/新增与修改追踪（本版只有当前文件状态）。
- 项目内直接创建 Python 执行任务、批量启动/重试与跨任务依赖。
- 输出文件的安全下载、预览或编辑。
- 桌面交互执行器和 GUI 浏览器的 Session 0 兼容性处理。
- 真正的系统重启恢复与生产环境迁移。

## 测试策略
- Rust `cargo test`：项目创建、文件路径防越界、鉴权、按任务归属、保存重载、删除不损坏任务、文件正文不泄露。
- `node --check frontend/assets/projects.js`：新前端脚本语法。
- 现有隔离模拟 `dev/simulate_task_runtime_binary.py` 和 SCM 服务测试继续确保调度逻辑没有回归。
