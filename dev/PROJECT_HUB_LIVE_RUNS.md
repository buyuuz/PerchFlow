# PerchFlow Project Hub — 实时执行详情与 Python 日志修复

## 问题来源

C2 用户将 `Photo_AutoPublisher.py` 加入独立 PerchFlow 测试包执行。运行过程中，项目页面未持续显示任务执行详情和日志，只有点击「刷新执行详情」后才看到完整日志。

对 V5 源码排查发现：

- `monitorTaskRun()` 只以 1 秒间隔短期轮询任务总体状态（最多 90 次），**并不轮询当前执行记录和日志**。
- `showProjectRuns()` 从后端获取一次 `/history`，但不在面板保持打开时持续刷新。
- 运行日志只有明确点击「按需查看该次日志」才读一次。
- Python 脚本 stdout 重定向到文件时可能使用块缓冲，`print()` 日志直到进程结束才完整落盘。
- `renderProjectDetail()` 刷新整个项目时会清空当前执行记录面板，造成监看中断。

## 修复方案

1. **执行详情打开后自动刷新**：单一 2 秒轮询，更新最近执行列表、运行状态、起止时间、耗时和退出码；新运行出现时，默认跟随最近一次。用户手动点击旧运行记录后不自动抢回焦点。
2. **日志显式授权后持续刷新**：仍需用户主动点击「按需查看该次日志」，然后约 2 秒重新读取同一次运行的最后 128 KiB 日志。只更新变化文本；保持日志滚动位置，接近底部才自动跟随；记录进入终态后最后读取一次。
3. **产出变化在任务完成后更新**：运行中仅显示待完成提示，不读取尚未生成的单次运行文件快照；终态返回后显示实际 `created/modified/removed` 摘要和文件变化。
4. **Python 即时刷出 stdout**：只有 Python 解释器命令才设置子进程环境 `PYTHONUNBUFFERED=1`；不修改用户原脚本、不额外设置全局变量，不影响非 Python 程序行为。
5. **不打断查看**：项目状态刷新不再隐藏同项目正在查看的历史详情；切换项目或关闭面板停止刷新，并检查 `project/run_id` 防止旧响应覆盖新选择。

## 安全与边界

- **未修改 Photo_AutoPublisher.py**，未访问真实 TikTok、紫鸟、ZClaw、Excel 或用户 C2。
- 不会自动启动、重试或重新发布任何任务。尤其不应因为页面没有变化而再次点击「运行一次」。
- 日志可能包含脚本自己打印的敏感信息，仍只在明确点击后读取；自动刷新仅作用于已授权显示的日志。
- 仅本地 HTTP API 读取现有任务状态和日志，没有添加新的外部连接或系统服务。
- 轮询是近实时（约 2 秒），不是 WebSocket 逐字符流。极长日志仍只展示最后 128 KiB。
- 如脚本通过后台子进程缓冲日志，仍可能取决于子进程实现；`PYTHONUNBUFFERED` 只影响识别出的 Python 主进程。

## 验证

- GitHub-hosted Windows Edge 模拟 API：执行详情无需手动刷新、日志明确点击后递增、任务结束后显示文件变化、手选旧记录保持、关闭面板停止轮询。
- GitHub-hosted Windows EXE：真实 Python 假脚本调用 `print()` 后等待 9 秒，验证运行状态仍为 running 时日志端点已可读取刚刚输出的文字；不允许访问生产脚本。
- 全量 cargo test / ZIP 打包 / Windows PowerShell 启停与 mock 工作目录回归。
- 所有 GitHub Actions 通过后才生成更新的本地测试 ZIP；不合并 main。

## C2 测试版更新步骤

测试包本质上只有一个带嵌入前端的 `perch.exe`，启动脚本和配置格式没有改动。如果继续使用此前已设置 Photo_AutoPublisher 的测试目录：

1. 先确认真实发布脚本已经执行完成，避免中途终止。
2. 双击 `Stop-Test.cmd` 停止**测试版实例**，不要操作正式版服务。
3. 备份整个测试目录，特别是 `perch.toml` 和 `task-logs`。
4. 将新 ZIP 内的 `perch.exe` 复制替换到**现有测试目录**，其他文件和配置不要覆盖。
5. 双击原来的 `Start-Test.cmd`，打开项目页面验证历史仍在、实时刷新生效。
6. 优先用无发布副作用的示例 Python 任务测试；不要为了测试刷新再次运行十条真实排期任务。

**发布候选与实际电脑运行仍是两个独立关卡，不自动升级原版。**
