# PerchFlow Project Hub V2 — 开发与验证记录

## 目标与取舍

在 V1 项目管理层上增加两项能力：

1. 在项目详情页直接创建 Python 启动任务（`POST /api/projects/:name/python-task`）。
2. 将**用户明确登记的**文件元数据变化关联到每个真实的 `run_id`，而非只看文件的当前状态。

保留现有的 `Scheduler`、`perch.toml`、任务历史和 API 鉴权，不另建任务调度器。

## Python 任务创建

- 从项目详情点击「+ Python 任务」，填写任务名称、解释器绝对路径、相对于项目根目录的 .py 脚本、逐行启动参数、Cron、超时。
- 后端检查项目目录与脚本确实存在、脚本不经链接跳到项目根目录外、名字不重复、Cron 有效。
- 后端**强制保存 enabled=false**，即使客户端传 enabled=true 也不能自动启动或定时执行。
- 将 Python 文件关联到项目输入文件，自动挂到同一项目任务下；继续从 `/tasks` 管理启用/停用、手动运行和日志。
- 不创建、复制、打开或执行任何业务文件，删除项目也不触碰关联脚本。

## 每次运行文件变化

- 在 Scheduler 运行子进程**前后**读取项目关联的 `inputs` + `outputs` 元数据。
- 只跟踪最多 128 个用户**显式登记的相对文件路径**，不递归扫描整个目录、不追踪未登记的新文件。
- 保存 `created/modified/removed`、文件类型、存在状态、大小、修改时间纳秒值；绝不读取或存储文件正文/哈希/账号密码/API Key。
- 新接口 `GET /api/tasks/:name/files/:run_id`，与现有日志相同使用 Bearer 鉴权；按次记录保存在 PerchFlow 原 `task-logs` 目录的 `*.files.json`，不改动项目原目录。
- 成功、失败、取消和超时后尝试记录；意外断电/强杀时尚未生成的记录会显示“不可用”，不能保证生成。
- 监测到的文件变化不等于能绝对证明由该任务导致：如果别的进程同时改动同一文件，结果是“运行时段内观察到变化”。
- 目录元数据可以登记，但**尚未深入枚举目录中的每个文件**；只看此目录自身的修改时间。

## 安全与隔离

- 所有代码只在 `feature/project-hub-v2`。真实用户电脑、Windows Task Scheduler、Daily_Check、Firecrawl 登录、TikTok 发布均不接触。
- 测试只使用 CI 临时文件夹、虚构账号文本、无网络业务请求的 MOCK_ONLY 命令。
- 已有任务的 stdout/stderr 由旧日志系统保留；脚本自行打印敏感内容仍会进入旧日志，本期文件追踪**不会**自动解决该问题。
- 采用严格相对路径 + canonical 路径包含检查，拒绝文件系统链接跳出项目根目录。
