# PerchFlow Project Hub V4 — 输入预检与执行结果汇总

## 本阶段目标
在已验证的 Project Hub V3 上，新增 **运行前输入依赖预检** 与 **按运行实例汇总执行结果**；继续复用同一个 Scheduler，不额外启动调度中心。

## 设计决定
1. 项目新增 `preflight_inputs = true/false`，默认 `false`。老项目、旧 TOML 与现有脚本维持原执行行为；不做强制迁移。
2. 用户启用后，脚本在每次 Cron/手动执行前检查项目登记的所有 `inputs` 相对文件路径：必须是存在于项目根目录内的常规文件，不接受越界或链接。
3. 最多检查 128 个输入文件。项目根目录不可访问或输入过多时，预检失败关闭：该次任务记录 `blocked`，**不启动 Python/命令子进程**。
4. 预检只读取路径元数据，不读取输入文件正文，也不验证密码或 Key 的有效性。输入文件仍保留原目录。
5. `/api/projects/:name/preflight` 为 Bearer 鉴权保护下的只读即时就绪检查，不启动任务。
6. 每次任务完成时，现有 `task-logs/history.jsonl` 追加 `duration_ms`、`preflight`、`output_summary`（新增/修改/删除计数与不完整扫描状态）、`files_recorded`，和已有 `run_id` 一同保存。
7. 输出计数只计算 `output` 文件变化，**不将目录本身算成产出文件**。如果本次被预检阻止，则不创建运行文件变化记录。
8. `/projects` 的执行历史可查看状态、耗时、退出码、预检是否通过，以及产出文件数量与详细变化。
9. 原始脚本日志依旧由现有 `/api/tasks/:name/log/:run_id` 提供。**不会自动加载/展示**；只有用户点击「按需查看该次日志」时才向后台请求，并用 textContent 展示，避免 HTML 注入。

## 注意事项
- `preflight_inputs` 是项目级开关；项目的多个任务共用同一份输入文件清单。尚不支持单任务独立覆盖。
- 预检只确认文件路径/元数据可用，不保证文件内容正确、解释器依赖齐全、网络连通或浏览器登录成功。
- 预检完成到脚本启动之间仍存在文件状态可能变化的竞态，因此它是最佳努力检查而非事务保障。
- `blocked` 是任务运行历史的独立状态（非 `failed`），会产生运行记录和错误原因，但没有新生成的子进程日志文件。
- 输出变化是观察运行期间的元数据差异，可能包含其他并发进程造成的修改；不读取文件正文。
- Python 或其他脚本自己打印的账号/密码/API Key 仍可能出现在原日志内。日志默认不打开，但不意味着旧日志已脱敏。
- 文件名与相对路径也可能包含敏感信息，建议专用输出目录不要使用密钥作为文件名。

## GitHub Hosted Windows 测试
- Rust 核心：输入缺失、多文件齐全、离线项目、路径越界、超过输入上限、默认不启用；不读正文。
- Rust API：预检未通过 -> Cron/手动启动阻止且不生成业务输出；补齐 MOCK 输入后可运行，并在 history 中显示新增文件数量和耗时。
- Rust API：旧配置没有开启预检时，缺少登记输入不影响原任务执行。
- Edge 只用模拟 API 的桌面/移动测试：显示就绪状态、可选预检勾选、执行摘要、用户明确点击后才读取日志。
- 现有 Release Build、Cron/取消/超时/日志恢复、SCM 临时服务回归继续运行。

## 安全范围
- 本轮代码只提交到 `feature/project-hub-v4`；**不修改 main、不部署、不接触用户电脑或其 Windows 计划任务**。
- 所有行为测试都用 GitHub-hosted Windows 临时目录与虚构 TXT、模拟 cmd 脚本，不执行 Daily_Check、Photos_Auto、Firecrawl 登录或 TikTok 发布。
